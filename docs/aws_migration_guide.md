# Overwatch AML — AWS Migration Guide

This document walks through moving the Overwatch AML pipeline from the laptop to AWS (Mumbai). You'll need ~1 hour the first time, mostly waiting on RDS to provision.

The architecture you're building:

```
                ┌─────────────────────────┐
                │  EC2 (t3.medium, Ubuntu)│
                │  - cron: run_all.sh     │      ┌─────────────────────────┐
   internet ──> │  - cron: monitor        │ ──>  │  RDS PostgreSQL 15      │
                │  - cron: daily_pipeline │      │  (db.t3.micro, 50 GB)   │
                │  - venv + Playwright    │      └─────────────────────────┘
                └────────────┬────────────┘                  ▲
                             │                                │
                             └──── reads/writes ──────────────┘
                             │
                ┌────────────▼────────────┐
                │  S3 bucket              │
                │  overwatch-aml-backups- │
                │  <account>-ap-south-1   │
                │  - migration tarballs   │
                │  - pg_dumps (versioned) │
                └─────────────────────────┘
```

Cost ballpark (Mumbai, on-demand, May 2026):
- EC2 t3.medium ≈ ₹2,400/mo
- RDS db.t3.micro ≈ ₹1,400/mo + 50 GB gp3 storage ≈ ₹460/mo
- S3 (versioned, ~5 GB initial) ≈ ₹15/mo
- Total ≈ **₹4,300/mo** (you can pause EC2 when not running to halve this)

---

## Prerequisites

- AWS account with an IAM user that has: EC2, RDS, S3, IAM (limited).
- AWS CLI configured locally (`aws configure`) with that user's access key.
- An SSH key pair in Mumbai region (`overwatch-key.pem` on your laptop).
- The current laptop is healthy — `crontab -l` shows 4 jobs and `psql` to the local DB works.

---

## Stage 1: Package the migration locally (your laptop)

```bash
cd ~/risk-pipeline
# Take a fresh pg_dump first so the migration uses today's data:
PGPASSWORD=aayush123 pg_dump -U aayush -d risk_pipeline -Fc -Z5 \
    -f /home/aayush/backups/risk_pipeline_backup_$(date +%Y%m%d).dump

# Now package and upload everything to S3:
./scripts/aws_migration.sh
```

The script will:
1. Create `s3://overwatch-aml-backups-<account>-ap-south-1` (versioned, encrypted, private)
2. Upload the pg_dump
3. Upload every per-source CSV in `data/`
4. Upload a code tarball (excludes `venv/`, `__pycache__`, `.git`, `.env`)
5. Write `docs/aws_migration_checklist.txt` with the S3 prefix you'll need on the EC2 side

**Note what it does NOT upload** (deliberate):
- `.env` and `.claude/settings.local.json` — your Slack webhook + DB password. Those ride a separate channel (`scp` later).
- `master_watchlist.csv` — that's a derived artifact regenerated by `combine.py`.

Make a note of the **S3 prefix** the script prints (e.g. `migration-20260520T103000Z`). You'll need it on the EC2 side.

## Stage 2: Provision RDS (postgresql)

Console → RDS → Create database:

| Field | Value |
|---|---|
| Engine | PostgreSQL 15.x |
| Templates | Free tier (or Production for backups + Multi-AZ) |
| DB instance identifier | `overwatch-risk-pipeline` |
| Master username | `aayush` |
| Master password | (generate, save in 1Password) |
| Instance type | `db.t3.micro` |
| Storage type | gp3, 50 GB, autoscaling to 200 GB |
| VPC | default |
| Public access | **No** |
| Security group | new — `overwatch-rds-sg` |
| Initial database name | `risk_pipeline` |
| Backup retention | 7 days |
| Maintenance window | Sun 03:00 IST |

Wait for status: **Available** (~8 min). Note the endpoint, e.g. `overwatch-risk-pipeline.cxxxxx.ap-south-1.rds.amazonaws.com`.

---

## Stage 3: Provision EC2

Console → EC2 → Launch instance:

| Field | Value |
|---|---|
| Name | `overwatch-aml-runner` |
| AMI | Ubuntu Server 24.04 LTS (HVM), SSD |
| Instance type | t3.medium (2 vCPU, 4 GB) |
| Key pair | `overwatch-key` (your existing one) |
| Network | default VPC, default subnet |
| Auto-assign public IP | Enable |
| Storage | 30 GB gp3 |
| Security group | new — `overwatch-ec2-sg`, inbound 22 from your home IP only |
| IAM instance profile | new role `overwatch-ec2-role` with: `AmazonS3ReadOnlyAccess` (or scoped policy below) |

Open the RDS security group inbound 5432 from `overwatch-ec2-sg` (NOT 0.0.0.0/0).

**Tighter S3 IAM policy** (recommended over `AmazonS3ReadOnlyAccess`):
```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:ListBucket"],
    "Resource": [
      "arn:aws:s3:::overwatch-aml-backups-<account>-ap-south-1",
      "arn:aws:s3:::overwatch-aml-backups-<account>-ap-south-1/*"
    ]
  }]
}
```

## Stage 4: Bootstrap the EC2 host

SSH in:
```bash
ssh -i ~/.ssh/overwatch-key.pem ubuntu@<ec2-public-ip>
```

Clone the repo:
```bash
git clone <your-github-repo-url> risk-pipeline
cd risk-pipeline
```

Run the bootstrap script (it requires the values from the previous stages):
```bash
export S3_BUCKET="overwatch-aml-backups-<account>-ap-south-1"
export S3_MIGRATION_PREFIX="migration-20260520T103000Z"   # the prefix from Stage 1
export PG_HOST="overwatch-risk-pipeline.cxxxxx.ap-south-1.rds.amazonaws.com"
export PG_USER="aayush"
export PG_PASSWORD="<the-rds-password-from-1Password>"
export PG_DB="risk_pipeline"
sudo -E ./scripts/setup_aws_ec2.sh
```

The script will:
1. Install Python 3.12, PostgreSQL client, Chromium + system libs for Playwright
2. Create the venv and install `requirements.txt`
3. Install Playwright browsers
4. Download the pg_dump from S3 and `pg_restore` into RDS
5. Write `.env` with the RDS credentials
6. Install three cron jobs (run_all 06:00, monitor 07:00, daily_pipeline 07:30)
7. Run `validate_production.py` as a smoke test
8. Send a Slack ping if the webhook is configured

Expected runtime: ~10 min (Playwright Chromium install is the slow step).

## Stage 5: Copy the secrets

These were NOT uploaded to S3 (correctly), so copy them directly:
```bash
# From your laptop:
scp -i ~/.ssh/overwatch-key.pem .env ubuntu@<ec2-public-ip>:~/risk-pipeline/.env
scp -i ~/.ssh/overwatch-key.pem .claude/settings.local.json \
    ubuntu@<ec2-public-ip>:~/risk-pipeline/.claude/settings.local.json
```

On EC2, make sure permissions are tight:
```bash
chmod 600 ~/risk-pipeline/.env ~/risk-pipeline/.claude/settings.local.json
```

## Stage 6: Verify

```bash
# row count
PGPASSWORD=$PG_PASSWORD psql -h $PG_HOST -U aayush risk_pipeline -c \
    "SELECT COUNT(*) FROM watchlist_records;"
# should be ~4.77M (whatever your dump had)

# entity graph
PGPASSWORD=$PG_PASSWORD psql -h $PG_HOST -U aayush risk_pipeline -c \
    "SELECT COUNT(*), MIN(created_at), MAX(created_at) FROM entity_groups;"

# extensions
PGPASSWORD=$PG_PASSWORD psql -h $PG_HOST -U aayush risk_pipeline -c \
    "SELECT extname FROM pg_extension ORDER BY extname;"
# expect: pg_trgm, pgcrypto, plpgsql, vector

# manual run (don't wait for 06:00)
./run_all.sh
# watch logs/cron.log

# fuzzy search smoke test
./venv/bin/python scripts/knowledge_graph.py --search "Asbat al-Ansar"
```

## Stage 7: Cut over from laptop

Only once Stage 6 looks healthy:
```bash
# On the laptop:
crontab -e
# Comment out (don't delete) the 4 lines:
#   0 6 * * * /home/aayush/risk-pipeline/run_all.sh ...
#   */30 * * * 1-5 /home/aayush/risk-pipeline/scripts/git_autopush.sh ...
#   0 7 * * * ... monitor_sources.py ...
#   30 7 * * * ... daily_pipeline.sh ...
```

Then wait for 06:00 IST tomorrow and watch `logs/cron.log` on EC2. If the first run is clean, run a Slack ping to confirm.

---

## Rollback (if something goes badly wrong)

The laptop crontab is only commented out — uncomment those 4 lines and you're back to the old setup.

The local PostgreSQL is unchanged — no data was moved off the laptop, only copied.

To delete the AWS resources without losing data: take a final RDS snapshot first, then delete the RDS instance and EC2.

## Operational tips for the EC2 host

- **Logs**: tail `~/risk-pipeline/logs/cron.log` for run_all output, `logs/daily_pipeline_*.log` for KG refreshes, `logs/monitor.log` for health snapshots.
- **Disk**: `/` is 30 GB. The biggest growth is `logs/` (rotate quarterly with `logrotate`) and `data/` (≈1.5 GB).
- **MCA enrichment**: as of 2026-05-20 the `scoreme.in` proxy is degraded (99.5% timeout). Keep the tmux session paused until you can verify the API; don't auto-retry.
- **WatchOutInvestors**: scraper is resumable (dedups by name+amount). If a run is cut short, just relaunch.

## Appendix B — Files NOT in the migration tarball

- `venv/` — recreated by `setup_aws_ec2.sh`
- `.git/` — clone fresh from GitHub
- `.env`, `.claude/settings.local.json` — secrets; copied via `scp`
- `data/master_watchlist.csv` — regenerated by `scripts/combine.py`
- `logs/`, `reports/`, `snapshots/`, `backups/` — local-only history
- `__pycache__/`, `*.pyc` — Python bytecode
